***Цель работы***

Целью лабораторной работы является изучение принципов автоматизации процессов непрерывной интеграции и непрерывной доставки программного обеспечения (CI/CD), а также получение практических навыков настройки конвейеров сборки, тестирования, проверки безопасности и развёртывания приложений с использованием GitHub Actions и Docker.

В рамках лабораторной работы необходимо реализовать два варианта CI/CD pipeline: некорректно настроенный pipeline, демонстрирующий плохие практики разработки, и улучшенный pipeline, включающий автоматические проверки качества кода, тестирование, сборку Docker-образа, сканирование уязвимостей и проверку работоспособности приложения.
Дополнительно необходимо изучить возможности инструмента Trivy для анализа безопасности контейнерных образов, сравнить результаты сканирования различных базовых образов и применить практики повышения безопасности и воспроизводимости сборки.

***2. Описание используемых технологий***
Для выполнения лабораторной работы были использованы следующие инструменты и технологии.
  
  Git и GitHub
    
    Git — система контроля версий, предназначенная для отслеживания изменений в исходном коде и совместной разработки программного обеспечения.
    GitHub — платформа для хранения Git-репозиториев, организации совместной работы и автоматизации процессов разработки. В данной работе GitHub использовался для хранения       проекта, управления версиями исходного кода и запуска CI/CD pipeline.
 
  GitHub Actions
    
    GitHub Actions — инструмент автоматизации рабочих процессов, встроенный в GitHub. Он позволяет создавать workflow, которые запускаются при наступлении определённых          событий, например при отправке изменений в репозиторий или создании pull request.
    В лабораторной работе GitHub Actions используется для автоматического выполнения проверок кода, запуска тестов, сборки и сканирования Docker-образа, публикации образа и     проверки работоспособности приложения.
  
  Python и Flask
    
    Python — язык программирования, на котором реализовано тестовое веб-приложение.
    Flask — микрофреймворк для разработки веб-приложений на Python. С его помощью реализованы HTTP-маршруты для взаимодействия с приложением.
  
  Pytest
    
    Pytest — инструмент для автоматизированного тестирования Python-приложений. Он позволяет проверять корректность работы отдельных функций и HTTP-маршрутов.
  
  Flake8
    
    Flake8 — инструмент статического анализа Python-кода. Он проверяет соответствие кода установленным правилам оформления и выявляет потенциальные ошибки.
  
  Docker
    
    Docker — платформа контейнеризации, позволяющая упаковывать приложение вместе с необходимыми зависимостями в контейнер.
    В лабораторной работе Docker используется для создания образа приложения и его последующего запуска в изолированной среде.
  
  Trivy
    
    Trivy — инструмент анализа безопасности, предназначенный для обнаружения известных уязвимостей в контейнерных образах, зависимостях и других компонентах программного        обеспечения.
    GitHub Container Registry
    GitHub Container Registry (GHCR) — хранилище контейнерных образов, интегрированное с GitHub. В рамках работы оно используется для публикации собранного Docker-образа.

## 1. Описание плохого CI/CD Pipeline

В рамках лабораторной работы был создан плохой CI/CD pipeline, предназначенный для демонстрации ошибок при настройке автоматизации сборки и проверки приложения.

В нём были использованы следующие плохие практики:

1. Использование устаревших версий GitHub Actions (actions/checkout@v2 и actions/setup-python@v2).
2. Отсутствие кеширования зависимостей, из-за чего при каждом запуске пакеты устанавливаются заново.
3. Отсутствие проверки безопасности Docker-образа.
4. Использование незакреплённых версий зависимостей.
5. Отсутствие полноценной проверки перед публикацией и развёртыванием приложения.

Также в pipeline специально не была установлена зависимость flake8, поэтому проверка кода завершалась ошибкой.

В результате плохой pipeline завершался с красным статусом Failed. Этап развёртывания не выполнялся, поскольку проверка кода не была пройдена.

Таким образом, было показано, что неправильно настроенный CI/CD pipeline может содержать ошибки и не обеспечивать необходимый контроль качества приложения.

Если обнаруживаются ошибки, дальнейшие этапы не запускаются.

***3. Сравнение результатов сканирования Trivy***
**«Мой образ весит 1 ГБ, но это не жир, это мышцы»**

Когда мы собрали первый образ на основе `python:3.13`, Trivy выдал столько уязвимостей, что казалось, будто мы скачали не базовый образ, а целый сундук с сокровищами. Но после перехода на `python:3.13-slim` наш «мальчик» похудел на 91,5% уязвимостей и стал выглядеть как после хорошего марафона. Теперь он не только компактнее, но и безопаснее.
Для оценки безопасности Docker-образов было проведено сканирование двух базовых образов:

- python:3.13 — полный базовый образ Python.
- python:3.13-slim — облегчённый вариант образа Python.

## 5. Проверка работоспособности приложения
**«Ты не ты, когда голоден... то есть, когда не отвечает /health»**

<img width="480" height="270" alt="image" src="https://github.com/user-attachments/assets/33335284-f5bb-46d2-aa6c-08050bacabbd" />

Для проверки работоспособности разработанного приложения был реализован специальный endpoint `/health`. Он предназначен для определения того, запущено ли приложение и может ли оно обрабатывать входящие HTTP-запросы.

Подобные проверки называются Healthcheck и широко используются при разработке и эксплуатации контейнеризированных приложений. Они позволяют автоматически определить, работает ли сервис после запуска, и выявить ситуации, когда контейнер запущен, но само приложение внутри него не отвечает.

В разработанном Flask-приложении маршрут `/health` обрабатывает GET-запрос. При успешном обращении сервер возвращает HTTP-статус 200 и JSON-ответ:

```json
{
    "status": "ok"
}
```

HTTP-статус 200 означает, что запрос был успешно обработан сервером. Поле `status` со значением `ok` дополнительно указывает на нормальное состояние приложения.

Для проверки endpoint используется команда:

```bash
curl --fail http://localhost:5000/health
```

Утилита curl отправляет HTTP-запрос на указанный адрес и выводит ответ сервера. Параметр `--fail` позволяет считать HTTP-ответы с ошибками неуспешными.

Проверка работоспособности также включена в Good CI/CD Pipeline. После сборки и публикации Docker-образа workflow загружает его из GitHub Container Registry и запускает контейнер. Затем выполняется запрос к endpoint `/health`.

Поскольку приложению может потребоваться некоторое время для запуска, в workflow предусмотрено несколько повторных попыток проверки с небольшими интервалами. Если приложение отвечает успешно, этап Healthcheck завершается с успешным результатом. Если после нескольких попыток ответ не получен, pipeline выводит журналы контейнера и завершается ошибкой.

Таким образом, Healthcheck позволяет проверить не только успешность сборки Docker-образа, но и фактическую работоспособность приложения после запуска. Это важно, поскольку успешное создание контейнера само по себе ещё не гарантирует, что приложение внутри него функционирует правильно.
