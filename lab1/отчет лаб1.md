## Цель работы
Целью нашей лабы было получение работающего результата: nginx, который держит сайт живым, даже когда один из бэкендов упал. 
Стоит вообще сказать что такое nginx. Это веб-сервер, который обрабатывает запросы от пользователей в браузере и отдает им сайты, картинки, стили и другие файлы, принимает запросы из интернета и передает их на внутренние серверы, защищая их и распределяя нагрузку (работает как обратный прокси-сервер) и распределяет поток посетителей между несколькими серверами, чтобы сайт не упал от перегрузки (работает как балансировщик нагрузки).  
Работали мы, разумеется, с нашим милейшим ежедневником из нулевой лабы.
## Настройка двух экземпляров бэкендов | ОН ОБЕЩАЛ ПОМОЧЬ, НО В ПОСЛЕДНИЙ МОМЕНТ СЛИЛСЯ
Чтобы наш список важнейших дел в самый неподходящий момент не поломался из-за отказа какого-нибудь процесса, мы делаем две копии бэкенда, которые распределяют между собой собственно запросы и продолжают принимать задачи типа **"Оформить кредитку т-банка по чьей-то реферальной ссылке"**. Очевидно, они должны быть друг от друга независимы. 

Для этого немного поменяем `lab1/backend/app.py`:
```
INSTANCE_NAME = os.getenv("INSTANCE_NAME", "backend-default")

if __name__ == "__main__":
    port = int(os.getenv("PORT", 5000))
    app.run(host="127.0.0.1", port=port, debug=True)
```
Что к чему: получаем значение переменной окружения операционной системы, в переменной PORT записываем порт (ого), на котором будет конкретный экземпляр. Если значение не задано, присваиваем ему дефолтное значение 5000. В инстанс нейм записываем имя порта, если оно не указано - просто оставляем там тоже имя по умолчанию. Кстати, чтобы мы могли увидеть, куда конкретно наш запрос уходит в данный момент, в функцию вывода информации добавляем еще одну мегастрочку: 
`response.headers["X-Backend-Instance"] = INSTANCE_NAME`.
Здесь мы, как несложно догадаться, просто выводим имя сервера, который соизволил наш запрос обработать. Он выделен зеленым на скрине

## Балансировка нагрузки и обратный прокси-сервер | ПОЛЬЗОВАТЕЛЬ НЕ ПОДОЗРЕВАЛ, ЧТО СКРЫВАЕТСЯ ВНУТРИ
Тут начинаем копаться в конфигурации nginx(файл nginx.conf если что). Объединяем наши экземпляры бэкендов в одну группу:
```
upstream backend_pool {
    server 127.0.0.1:5001;
    server 127.0.0.1:5002;
}
```
К этим серверам nginx может обращаться. Связь.

Чтобы наш никому не известный пользователь не попал куда не надо, займемся проксированием. 
```
location /api/ {
    proxy_pass http://backend_pool/;
}
```
Ну то есть все запросы, которые начинаются с `\api\` мы направляем на серверы, которые непосредственно мы указали в группе доступных (бэкенд пул). 

Вместе с этим уделим внимание и фронтенду: ранее мы напрямую обращались к приложению (`const API_URL = "http://127.0.0.1:5000/tasks";`). Теперь у нас все по-другому:
```
const API_URL = "/api/tasks";
```
Все запросы теперь проходят через nginx, вариантов нет.

## Настройка HTTPS и перенаправления HTTP-запросов | ОНИ ХОТЕЛИ УКРАСТЬ ВСЮ ИНФУ, НО НЕ ТУТ-ТО БЫЛО
Для настройки HTTPS нам был нужен сертификат, в рамках лабы хватает самоподписанного. Для работы в этой части возьмем утилиту OpenSSL. 

<img width="396" height="154" alt="image" src="https://github.com/user-attachments/assets/ba0beff8-683b-477e-a521-8fb212a7ccc9" />

В итоге получаем сертификат и ключ. Но их я вам не покажу, потому что нельзя. 

Вместо этого давайте лучше посмотрим, как мы меняем конфигурацию nginx для работы с HTTPS:
```
server {
    listen 443 ssl;
    server_name localhost daily.local;

    ssl_certificate C:/nginx/cert/cert.pem;
    ssl_certificate_key C:/nginx/cert/key.pem;

    ...
}
```
Указываем, что сервер должен принимать HTTPS-соединения на порту 443 с использованием TLS.

Для обязательного использования защищённого соединения был настроен отдельный серверный блок на порту 80:
```
server {
    listen 80;
    server_name localhost daily.local second.local;

    return 301 https://$host$request_uri;
}
```

## Статические файлы и использование alias | ОН ОКАЗАЛСЯ НЕ ТЕМ, ЗА КОГО СЕБЯ ВЫДАВАЛ
Отдельно мы настраиваем nginx, чтобы он мог обрабатывать те файлы, для которых не требуется никакая серверная работа (типа html-разметки), самостоятельно. Для этого используем директиву root и показываем, где он должен искать запрашиваемые файлы. 
```
location / {
    root C:/Users/admin/.vscode/DevOps/skip/lab1/frontend;
    index index.html;
}
```

Часть материалов, положим, мы хотим хранить отдельно. В нашем конкретном случае это играет исключительно показательную роль. Так вот, если мы хотим что-то вынести отдельно, то будем использовать alias - что-то типа ярлыка для нашей папки с инфой. 
```
location /docs/ {
    alias C:/Users/admin/.vscode/DevOps/skip/lab1/docs/;
    index info.html;
}
```
Теперь при обращении к `\docs` рассматривается не корневая папка фронтенда, а наша папка.

## Ограничение частоты запросов | МЫ ЕЛЕ ВЫДЕРЖАЛИ НАТИСК. ПРЯМОЙ РЕПОРТАЖ
Если бы особо занятой человек попробовал бы с нереальной частотой добавлять свои задачи в ежедневник, это привело бы к снижению производительности нашего приложения либо же вообще поломало всю его работу. Нам такого не надо, поэтому необходимо ограничить частоту запросов в секунду. Если вы адекватный пользователь и не пытаетесь внести каждой свой шаг в список дел со скоростью 100 запросов/сек, то вы об установленном ограничении даже не узнаете, но приложение тем не менее будет защищено.

Для этого используем две директивы.  В блок http добавляем следующее:  
`limit_req_zone $binary_remote_addr zone=api_limit:10m rate=5r/s;`  
Айпи клиента в двоичном ключе, область памяти запросов на 10 МБ, ограничение на 5 запросов/сек. Очевидно.

Для того, чтобы использовать созданную зону внутри блока `\api\` делаем следующее в конфиге:

```
location /api/ {
    limit_req zone=api_limit burst=5 nodelay;
    limit_req_status 429;

    proxy_pass http://backend_pool/;
}
```

Тут, кстати, небольшое превышение (всплеск) сверх установленной нормы мы допускаем. Ну и если частота превышается, задаем код 429 Too Many Requests. Теперь nginx блокирует излишние запросы еще до их попадания во фласк.

## Страница 404 | ЭТА ОШИБКА СТАЛА РОКОВОЙ. ПОЛНАЯ ИСТОРИЯ
Вот здесь-то, в отличие от дизайна страницы второго хоста, стоило геройствовать. В случае, если какой-то пользователь недостаточно внимательно вводил в поисковик адрес сайта с нашего сервера, нам надо гордо ему об этом сообщить в фирменном стиле.  
Это несложно. В папке фронтенда создаем html-файл для страницы 404, туда непосредственно вносим всю разметку для страницы ошибки (см. файл `lab1/frontend/404.html`).  
Возвращаемся к настройкам конфига nginx. В блок основного сервера вносим инфу о странице 404: 

```
server {
    listen 443 ssl;
    server_name localhost daily.local;
    error_page 404 /404.html;

location = /404.html {
    root C:/Users/admin/.vscode/DevOps/skip/lab1/frontend;
    internal;
}
```
`internal` это что? Это директива, которая указывает, что этот блок у нас используется для внутренних запросов.  
Попробуем теперь обратиться к несуществующей странице: 
```

```

## Базовая авторизация | НИКТО НЕ ПОДОЗРЕВАЛ, КАКИЕ СЕКРЕТЫ ОН СКРЫВАЛ
Сделаем так, чтобы при обращении к определенным частям сайта программа требовала бы от пользователя логин и пароль.  
Для этого с помощь OpenSSL сгенерируем хэш пароля (сам пароль задаем сами, как несложно догадаться): `& "C:\Program Files\OpenSSL-Win64\bin\openssl.exe" passwd -apr1`.  
И логин, и хэш пароля будут храниться в одном файле `.htpassword` в формате `имя: хэш`. Эти данные сливать не рекомендуется в целях безопасности информации.  
Теперь надо сообщить конфигу nginx о нововведениях. 
```
location = /admin {
    auth_basic "Restricted Area";
    auth_basic_user_file C:/Users/admin/.vscode/nginx/conf/.htpassword;

    alias C:/Users/admin/.vscode/DevOps/skip/lab1/frontend/admin.html;
}
```
Зафиксировали: путь к файлу с логином и паролем, что нужно вернуть пользователю при успешной авторизации и название защищенной области.
