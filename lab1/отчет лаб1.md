## Цель работы
Целью нашей лабы было получение работающего результата: nginx, который держит сайт живым, даже когда один из бэкендов упал. 
Стоит вообще сказать что такое nginx. Это веб-сервер, который обрабатывает запросы от пользователей в браузере и отдает им сайты, картинки, стили и другие файлы(веб-сервер), принимает запросы из интернета и передает их на внутренние серверы, защищая их и распределяя нагрузку(обратный прокси-сервер) и распределяет поток посетителей между несколькими серверами, чтобы сайт не упал от перегрузки(балансировщик нагрузки).
Работали мы, разумеется, с нашим милейшим ежедневником из нулевой лабы.
## Настройка двух экземпляров бэкендов | ОН ОБЕЩАЛ ПОМОЧЬ, НО В ПОСЛЕДНИЙ МОМЕНТ СЛИЛСЯ
Чтобы наш список важнейших дел в самый неподходящий момент не поломался из-за отказа какого-нибудь процесса, мы делаем две копии бэкенда, которые распределяют между собой собственно запросы и продолжают принимать задачи типа **"Оформить кредитку т-банка по чьей-то реферальной ссылке"**. Очевидно, они должны быть друг от друга независимы. 

Для этого немного поменяем `lab1/backend/app.py`:
```
INSTANCE_NAME = os.getenv("INSTANCE_NAME", "backend-default")

if __name__ == "__main__":
    port = int(os.getenv("PORT", 5000))
    app.run(host="127.0.0.1", port=port, debug=True)
```
Что к чему: получаем значение переменной окружения операционной системы, в переменной PORT записываем порт (ого), на котором будет конкретный экземпляр. Если значение не задано, присваиваем ему дефолтное значение 5000. В инстанс нейм записываем имя порта, если оно не указано - просто оставляем там тоже имя по умолчанию. Кстати, чтобы мы могли увидеть, куда конкретно наш запрос уходит в данный момент, в функцию вывода информации добавляем еще одну мегастрочку: 
`response.headers["X-Backend-Instance"] = INSTANCE_NAME`.
Здесь мы, как несложно догадаться, просто выводим имя сервера, который соизволил наш запрос обработать. Он выделен зеленым на скрине

## Балансировка нагрузки и обратный прокси-сервер | ПОЛЬЗОВАТЕЛЬ НЕ ПОДОЗРЕВАЛ, ЧТО СКРЫВАЕТСЯ ВНУТРИ
Тут начинаем копаться в конфигурации nginx(файл nginx.conf если что). Объединяем наши экземпляры бэкендов в одну группу:
```
upstream backend_pool {
    server 127.0.0.1:5001;
    server 127.0.0.1:5002;
}
```
К этим серверам ngimx может обращаться. Связь.

Чтобы наш никому не известный пользователь не попал куда не надо, займемся проксированием. 
```
location /api/ {
    proxy_pass http://backend_pool/;
}
```
Ну то есть все запросы, которые начинаются с `\api\` мы направляем на серверы, которые непосредственно мы указали в группе доступных (бэкенд пул). 

Вместе с этим уделим внимание и фронтенду: ранее мы напрямую обращались к приложению (`const API_URL = "http://127.0.0.1:5000/tasks";`). Теперь у нас все по-другому:
```
const API_URL = "/api/tasks";
```
Все запросы теперь проходят через nginx, вариантов нет.

## Настройка HTTPS и перенаправления HTTP-запросов | ОНИ ХОТЕЛИ УКРАСТЬ ВСЮ ИНФУ, НО НЕ ТУТ-ТО БЫЛО
Для настройки HTTPS нам был нужен сертификат, в рамках лабы хватает самоподписанного. Для работы в этой части возьмем утилиту OpenSSL. 

<img width="396" height="154" alt="image" src="https://github.com/user-attachments/assets/ba0beff8-683b-477e-a521-8fb212a7ccc9" />

В итоге получаем сертификат и ключ. Но их я вам не покажу, потому что нельзя. 

Вместо этого давайте лучше посмотрим, как мы меняем конфигурацию nginx для работы с HTTPS:
```
server {
    listen 443 ssl;
    server_name localhost daily.local;

    ssl_certificate C:/nginx/cert/cert.pem;
    ssl_certificate_key C:/nginx/cert/key.pem;

    ...
}
```
Указываем, что сервер должен принимать HTTPS-соединения на порту 443 с использованием TLS.

Для обязательного использования защищённого соединения был настроен отдельный серверный блок на порту 80:
```
server {
    listen 80;
    server_name localhost daily.local second.local;

    return 301 https://$host$request_uri;
}
```
